STEP 1 - FRESH PROJECT SETUP (POWERSHELL)
-----------------------------------------

Open PowerShell in the project folder:
  cd C:\xampp\htdocs\mallow-billing

Install PHP dependencies:
  composer install

Create local environment settings:
  Copy-Item .env.example .env
  php artisan key:generate

Before migrating, open .env and configure DB_CONNECTION, DB_DATABASE,
DB_USERNAME, and DB_PASSWORD for the database you intend to use:
  notepad .env

IMPORTANT: Run migrations against a new, empty database for a clean setup.
The existing local MySQL database was reported to have an older schema with
manual changes. Do not blindly run the create-tables migration against that
database. Back it up and create/use a separate empty database first.

Create the schema:
  php artisan migrate

Create a merchant workspace:
  php artisan billing:merchant-create "Acme Corp"

The command prints the Merchant ID and API key once. Copy the key directly
into a password manager or another secure place. Do not put it in source
code, screenshots, this guide, or a Git commit.

Run the app:
  php artisan serve

Open this in the browser:
  http://127.0.0.1:8000

Sign in using the merchant ID and the API key. The login page asks for the
key; it is not the merchant name or database password.

1. 60-90 SECOND INTRODUCTION (ENGLISH)
--------------------------------------

"I built a Laravel 12 billing application for merchants that need to manage
customers, plans, subscriptions, usage, and invoices. The main challenge was
making usage ingestion tenant-safe and idempotent while preserving the correct
pricing when a subscription changes plans mid-cycle.

"I organized the billing logic into services. Usage requests are authenticated
with a merchant API key, validated, associated with the subscription segment
that was effective at the event time, and protected by a merchant-scoped
idempotency key. Subscription segments store pricing snapshots, so an invoice
can calculate prorated base fees and overage using the prices that were in
effect for each part of the billing period. Monetary calculations use BCMath
instead of floating-point arithmetic.

"I also added queued daily usage aggregation, scheduled invoice processing,
merchant dashboard pages and a JSON dashboard endpoint. The latest full test
run passed 26 tests and 171 assertions. I have not run a five-million-row
load benchmark or simulated true concurrent database connections."


2. PROJECT IN ONE SENTENCE
--------------------------

Merchant -> Customers -> Plans -> Subscriptions -> Plan-pricing segments ->
Usage events -> Daily usage rollups -> Invoices and invoice items -> Dashboard.

Each merchant owns its own business data. A usage event is tied to both a
subscription and the exact pricing segment effective at its occurrence time.

4. IMPORTANT FLOWS TO EXPLAIN
-----------------------------

A. Usage ingestion
   1. Client sends POST /api/usage with X-Merchant-Id and X-API-Key headers.
   2. AuthenticateMerchantApiKey checks the stored password hash.
   3. Middleware puts the verified merchant ID on the request. Throttling is
      configured to identify the authenticated merchant.
   4. RecordUsageRequest validates fields such as subscription ID,
      idempotency key, units, and timestamp.
   5. UsageController checks that the subscription belongs to this merchant
      and is active, then finds the segment whose time range contains the
      event's occurred_at.
   6. The event is inserted with merchant, customer, subscription, and segment
      IDs. The database unique key on (merchant_id, idempotency_key) is the
      final protection against duplicate writes, including concurrent retries.
   7. A matching retry returns HTTP 200; a new record returns HTTP 201; using
      the same key for a different payload returns HTTP 409.

B. Mid-cycle plan change
   1. Find and lock the merchant-owned active subscription.
   2. Confirm the effective time is inside its current billing period.
   3. Find the segment active at that time.
   4. Do not allow rewriting history if usage already exists after the
      requested effective time.
   5. Close the old segment at the change time and insert a new segment with
      a snapshot of the new plan's price and allowance.
   Result: usage before the change stays priced under the old segment; usage
   after it is priced under the new segment.

C. Invoice creation
   1. Lock the subscription and check whether that subscription-period invoice
      already exists.
   2. Select all pricing segments overlapping the invoice period.
   3. For each segment, calculate the overlap duration / full cycle duration.
   4. Multiply the segment base fee and included allowance by that ratio.
   5. Sum usage for that segment and period slice; charge only units above the
      prorated allowance using that segment's saved overage rate.
   6. Use BCMath decimal strings; persist invoice and line items together in
      a transaction.
   7. Unique invoice-period constraint and row locking help keep retries from
      creating duplicate invoices. A currency change within one invoice period
      is rejected rather than adding unlike currencies.

D. Daily usage aggregation
   Raw usage_events remain the detailed record. AggregateDailyUsage groups
   events by merchant/customer/subscription/segment for one calendar date,
   clears that date's old derived rows, and inserts fresh grouped totals in
   500-row batches within a transaction. Re-running the date replaces the
   result rather than adding to it a second time.
   Recovery command:
     php artisan billing:aggregate-usage 2026-10-28
   Scheduler and queue worker must be running for queued work to execute.


5. IF THE INTERVIEWER ASKS "WHY DID YOU DESIGN IT THIS WAY?"
------------------------------------------------------------

Why store a pricing snapshot in subscription_segments?
  Plans can be edited later. An invoice for historical usage must use the
  price and allowance that applied at that time, not the current plan values.

Why use an idempotency key?
  Clients retry requests after timeouts. The merchant-scoped unique key lets a
  retry return the original event without double-counting usage. Conflicting
  payloads are explicitly rejected.

Why both a code check and a database unique constraint?
  The early lookup gives a friendly replay response. Two requests can still
  race after that lookup, so the unique database constraint is the final
  correctness guarantee; the duplicate-key path then reads the winner.

Why use BCMath?
  Binary floating-point can produce rounding errors in money calculations.
  BCMath keeps calculations in decimal strings and the code rounds at defined
  persistence boundaries.

Why use transactions and row locks?
  Invoice creation involves several related writes; a transaction avoids a
  partially written invoice. Locking a subscription serializes billing-cycle
  advancement for that subscription. A unique constraint adds another layer
  of duplicate protection.

Why have raw events and daily_usage?
  Raw events preserve detailed, auditable usage and support invoice
  reconciliation. Daily rollups are derived data for aggregation/reconciliation.
  The current dashboard still reads indexed raw events; the rollup is not yet
  the dashboard query source.

Why queue daily aggregation and invoices?
  These jobs can take time and should not block a web request. Retries and a
  recovery command help handle transient failures. In production, operate a
  durable queue and monitor failures and queue lag.

Why not claim five-million-row performance?
  There is no measured benchmark in this project. The README describes index,
  batching, partitioning and retention trade-offs, but those are design
  considerations, not test results. I would benchmark with production-like
  data and hardware before making a throughput claim.


6. LIKELY QUESTIONS AND SHORT ANSWERS
-------------------------------------

Q: How do you prevent one merchant reading another merchant's data?
A: Authenticate the merchant first, use that verified ID in queries, and
   compare it with requested resource ownership. Feature tests cover tenant
   mismatch, including invoice detail access.

Q: What happens when the same usage request arrives twice?
A: Same merchant, key, and payload returns the original record with 200.
   Same key but different subscription, units, or timestamp returns 409.
   A unique database key prevents a race from inserting both.

Q: How do you handle a plan change during a billing month?
A: Split the subscription into effective-time segments. Invoice each segment's
   own prorated time, allowance, and overage using its pricing snapshot.

Q: How do you make an invoice job retry-safe?
A: Lock the subscription, check the invoice for that period, and rely on a
   unique subscription-period constraint. The writes occur transactionally.

Q: How can I manually generate and view invoices?
A: Click Generate due invoices on the dashboard. Generated invoices appear
   in the Invoices section. Click the eye icon to inspect the customer,
   billing period, status, line items, and total. A print button is available.
   The synchronous CLI command is also available; scheduled billing queues
   GenerateDueInvoicesJob.

Q: What does the rate limit apply to?
A: Usage API requests have a configurable per-authenticated-merchant limit.
   Authentication middleware is ordered before throttling so the limiter can
   key on the verified merchant, rather than relying on a client-supplied ID.

Q: What would you improve next?
A: I would add production-like load and concurrency tests, inject database
   failures around invoice creation, add observability for queue/job failures,
   and evaluate completed-day dashboard reads from daily aggregates only after
   defining a reconciliation and freshness policy. I would also add a schema
   upgrade migration for any existing legacy database rather than manually
   altering it.
